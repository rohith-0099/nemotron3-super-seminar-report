\chapter{Training}
\label{ch:training}

Training \NS\ has two parts. \emph{Pretraining} teaches the base model
language and knowledge from 25 trillion tokens of text and then extends it to
long contexts. \emph{Post-training} turns the base model into an assistant and
agent through supervised fine-tuning followed by reinforcement learning. The
overall sequence is:
\begin{enumerate}
  \item pretrain on 25 trillion tokens in NVFP4 precision;
  \item extend the context length to one million tokens;
  \item fine-tune on more than 7 million supervised samples;
  \item apply reinforcement learning for coding, mathematics, tool use and
        interaction quality; and
  \item retrain (``heal'') the MTP heads.
\end{enumerate}

\section{NVFP4 Pretraining}

\subsection{The NVFP4 Format}

Large models are normally trained in BF16, a 16-bit floating-point format, and
more recently in 8-bit FP8. \NS\ goes a step further and is pretrained mostly
in NVFP4, a 4-bit format that is natively accelerated on NVIDIA Blackwell
GPUs~\cite{nvidia2025nvfp4}. Fewer bits per number mean less memory traffic and
faster matrix multiplications, but at most sixteen distinct values can be
represented, so the format has to be designed carefully.

NVFP4 stores each value as a 4-bit E2M1 element: one sign bit, two exponent
bits and one mantissa bit. Values are grouped into micro-blocks of 16 elements,
and each block carries its own 8-bit (E4M3) scale factor chosen so that the
largest value in the block maps to the largest representable FP4 value. A
second-level FP32 scale is applied per tensor (Figure~\ref{fig:nvfp4-format}).
The block scale costs 8 bits per 16 values, so the format uses about 4.5 bits
per value on average. Compared with the alternative MXFP4 format, NVFP4 uses
smaller blocks and a finer-grained scale, which is the reason for its better
accuracy.

\subsection{The Training Recipe}

Simply rounding everything to 4 bits makes training diverge. The NVFP4
recipe~\cite{nvidia2025nvfp4,nvidia2025nemotron3} relies on several techniques
that are all used in \NS:
\begin{itemize}
  \item Weights, activations and gradients are all quantized to NVFP4 for the
        forward pass and for both gradient computations of each linear layer.
  \item Weights use \emph{two-dimensional} block scaling so that the same
        quantized weights are seen in the forward and the backward pass, while
        activations and gradients use one-dimensional blocks.
  \item \emph{Random Hadamard Transforms} are applied to the inputs of the
        weight-gradient computation to spread out outliers within a block.
  \item \emph{Stochastic rounding} is applied to gradient tensors, so that the
        rounding error is unbiased.
  \item A small set of sensitive layers is kept at higher precision.
\end{itemize}
Figure~\ref{fig:nvfp4-loss} shows the result that motivated the approach: on a
12B model the NVFP4 validation loss stays close to the FP8 baseline over 10
trillion tokens.

\subsection{Observations from 25 Trillion Tokens}

\NS\ demonstrates stable NVFP4 training over the full 25-trillion-token
horizon. The report also documents a side effect. During training the number
of weight-gradient elements that are exactly zero kept growing, reaching 7\%
of all parameters by the end, and in some expert layers the norms of certain
channels shrank towards zero. To check that this was not a sign of unhealthy
training, the authors ran a controlled comparison on the smaller \NN\
architecture (Figure~\ref{fig:nvfp4-zeros}). NVFP4 training produced roughly
three times more zero-valued weight gradients than BF16 at the same point, and
the count fell back to the baseline when a partly trained NVFP4 model was
switched to BF16. The explanation offered is that 4-bit quantization underflows
gradients that are already very small to exactly zero, so low-norm channels
fade more quickly; a BF16 model shows the same pattern, only much later in
training.

  \caption[Zero-valued weight gradients under NVFP4 and BF16 training]{Number
  of zero-valued weight-gradient elements on \NN: the released BF16 model
  (left) and a 1T-token ablation in BF16 and NVFP4 (right). \source{NVIDIA
  (2026)~\cite{nvidia2026super}, Fig.~7}}
  \label{fig:nvfp4-zeros}
\end{figure}

The authors also tested whether switching to higher precision near the end of
training would help. Promoting all tensors to MXFP8 at 19T tokens improved the
loss curve but gave no sustained gain on downstream tasks
(Figure~\ref{fig:nvfp4-healing}), so the released model was pretrained with
the NVFP4 recipe for the entire run.

\section{Pretraining Data}

The pretraining corpus spans 16 high-level categories and follows the \NN\
data mixture~\cite{nvidia2025nano3}. The largest component is web-crawl data,
divided into quality tiers together with synthetic rewrites of the
higher-quality tiers. The remainder covers mathematics, Wikipedia, code,
academic text, multilingual data, PDF-derived text and synthetic
instruction-style data for general, STEM and coding topics.

New synthetic datasets were added for \NS\ and released publicly as
\emph{Nemotron-Pretraining-Specialized-v1.1}:
\begin{itemize}
  \item \textbf{Code concepts:} about 15 million Python problem--solution
        pairs generated from a taxonomy of programming concepts and validated
        by parsing.
  \item \textbf{Unconditional algorithmic problems:} algorithmic and
        LeetCode-style problems with edge cases and unit tests, de-duplicated
        and de-contaminated against standard coding benchmarks.
  \item \textbf{Economics and formal logic:} multiple-choice and worked
        problems with step-by-step solutions, verified by a model.
  \item \textbf{Multiple choice:} about 3.5 million MMLU-style questions with
        reasoning, kept only when several independent solutions agreed.
\end{itemize}

Training uses a two-phase curriculum (Figure~\ref{fig:blends}). Phase~1,
covering the first 80\% of training (20 trillion tokens), emphasises diversity
and broad coverage. Phase~2, the remaining 20\% (5 trillion tokens), shifts
towards high-quality sources such as Wikipedia to refine accuracy.

\section{Optimisation Setup}

Pretraining uses the AdamW optimiser (weight decay 0.1, $\beta_1 = 0.9$,
$\beta_2 = 0.95$) with a Warmup--Stable--Decay learning-rate schedule. The
learning rate is warmed up over the first 200 billion tokens to a peak of $4.5
\times 10^{-4}$, held constant, and then decayed over the final 5 trillion
tokens to $4.5 \times 10^{-6}$. The sequence length is 8192 tokens and the
batch size is 3072 sequences, about 25 million tokens per step.

While the learning rate is constant, individual checkpoints give noisy
benchmark scores. Rather than running separate decay runs to measure progress,
the team \emph{merged} checkpoints---a weighted average over a sliding window
of recent checkpoints---and evaluated the merged model. The best merge
outperformed the corresponding raw checkpoint by 2--4 points on average over
twelve benchmarks during the stable phase (Figure~\ref{fig:merge}), and the
report estimates that avoiding dedicated decay runs could save on the order of
16\% of the pretraining compute. The gap closes during the final decay phase.
The base checkpoint chosen for post-training was itself a merge over a
500-billion-token window.

\section{Long-Context Extension}

Pretraining uses sequences of 8192 tokens, far short of the one-million-token
target. A dedicated long-context phase is therefore added at the end of
pretraining. The model continues training at a constant learning rate of $4.5
\times 10^{-6}$ on a blend of 20\% long-document question-answering data and
80\% Phase~2 data, in two stages:
\begin{enumerate}
  \item 34 billion tokens at a context length of 1{,}048{,}576 tokens;
  \item 17 billion tokens alternating between 1M-token and 4k-token sequences,
        added to remove a small regression on mathematics benchmarks.
\end{enumerate}
Training on million-token sequences needs heavy parallelism: the report cites
64-way context parallelism, 2-way tensor parallelism and 64-way expert
parallelism on GB200 GPUs. The hybrid architecture is what makes this
practical, because 80 of the 88 layers have no quadratic cost.

\subsection{Two-Stage Objective}

The SFT stage trains on more than 7 million samples. NVIDIA found that a
single-stage SFT noticeably degraded performance on tasks with long inputs and
short outputs, and therefore used two stages with different loss
normalisation. For a batch $\mathcal{B}$ of conversations $c$, with
$\mathcal{O}_c$ the output-token positions of conversation $c$ and $\ell_t$
the negative log-likelihood of token $t$, Stage~1 averages over all output
tokens in the batch,
\begin{equation}
  \mathcal{L}_{\text{tok}} =
  \frac{\sum_{c \in \mathcal{B}} \sum_{t \in \mathcal{O}_c} \ell_t}
       {\sum_{c \in \mathcal{B}} |\mathcal{O}_c|},
\end{equation}
which gives strong token-level supervision and induces reasoning behaviour.
Stage~2 first averages within each conversation and then across conversations,
\begin{equation}
  \mathcal{L}_{\text{samp}} =
  \frac{1}{|\mathcal{B}|} \sum_{c \in \mathcal{B}}
  \left( \frac{1}{|\mathcal{O}_c|} \sum_{t \in \mathcal{O}_c} \ell_t \right),
\end{equation}
so that conversations with very long outputs no longer dominate the loss. This
restores the long-input, short-output behaviour while retaining the reasoning
ability. Stage~1 packs sequences up to 256k tokens; Stage~2 packs up to 512k
tokens and adds long-context data. The shared-weight MTP head continues to be
trained throughout with the same 0.3 loss weight.

\subsection{Data Blend}

Compared with \NN, the volume and diversity of agentic data were greatly
increased, and it takes a much larger share of the blend
(Figure~\ref{fig:sft-blend}). New or heavily revised datasets cover software
engineering on real GitHub issues, agentic command-line programming, terminal
use, web search, SQL, conversational and general-purpose tool calling,
financial reasoning, CUDA programming, long-context tasks, multilingual data
and safety.

samples.

\section{Reinforcement Learning}

The RL phase has three stages followed by MTP healing.

\subsection{Stage 1: RL from Verifiable Rewards}

The main stage is multi-environment RL from verifiable rewards (RLVR), in
which a response earns a reward that can be checked automatically---a correct
final answer, passing unit tests, a valid tool call. \NS\ is trained jointly on
21 environments and 37 datasets covering mathematics, code, STEM, safety,
chat, instruction following, long context, puzzles and several agentic tasks.
Training on all environments at once gave stable gains, whereas training on a
single environment caused severe regressions elsewhere.

As in \NN, prompts that the SFT model already answers correctly every time are
filtered out and the rest are ordered by difficulty. The benefit of such a
curriculum was shown in the \NN\ report (Figure~\ref{fig:rl-curriculum}).

\begin{figure}[htbp]
  \centering
  \includegraphics[width=\linewidth]{nano3-fig07-rl-curriculum.pdf}
  \caption[Curriculum sampling versus random sampling in RL]{Curriculum
  sampling compared with random sampling during RL on \NN, the recipe reused
  for \NS. \source{NVIDIA (2025)~\cite{nvidia2025nano3}, Fig.~7}}
  \label{fig:rl-curriculum}
\end{figure}

The algorithm is an asynchronous form of GRPO in which training and inference
run on separate GPUs. Inference workers generate trajectories continuously
into a buffer; when a batch is full it is sent to the trainer, and updated
weights are pushed back to the workers, which are never allowed to lag more
than one step behind. Each step samples 256 prompts with 16 responses each, a
batch of 4096, with a maximum generation length that starts at 49K tokens and
is later raised to 64K.

For long-horizon agentic domains the team uses \emph{PivotRL}, which reuses
expert trajectories from SFT and concentrates training on the ``pivot'' turns
where the model is uncertain about its next action. This keeps the efficiency
of SFT without the out-of-domain degradation it tends to cause.

\subsection{Stage 2: RL for Software Engineering}

Software-engineering tasks are trained in a separate stage because their
rollouts are much slower and need longer contexts. Each rollout launches a
container with the target repository, runs an agent loop to produce a code
patch, and scores it against the ground-truth tests for a binary reward. The
agent is exposed to several tool formats so that the skills transfer across
coding harnesses.

\subsection{Stage 3: RL from Human Feedback}

The last RL stage improves instruction following, robustness and overall
interaction quality. A large generative reward model (GenRM), trained on human
preference data and able to follow stated principles, scores the responses.
Unlike in \NN, this reward model is also used throughout the multi-environment
stage.

\subsection{MTP Healing}

RL changes the main model's behaviour, which leaves the MTP heads slightly out
of step with it. In the final stage the rest of the network is frozen and only
the MTP heads are retrained on the model's own generated responses, which the
report says significantly improves MTP accuracy---and therefore the speed-up
from speculative decoding.
