\chapter{Quantization and Deployment}
\label{ch:quant}

After training, NVIDIA applies post-training quantization and releases an FP8
checkpoint for Hopper GPUs and an NVFP4 checkpoint for Blackwell
GPUs~\cite{nvidia2026super}.

\section{FP8 and NVFP4 Checkpoints}

In the FP8 checkpoint the MoE experts and Mamba linear layers---where most
computation happens---are quantized to FP8, the KV cache is FP8, and the Mamba
state cache is stored in FP16.

The NVFP4 checkpoint targets prefill-heavy workloads such as coding agents. Its
recipe chooses each weight block's scale by minimising mean squared error,
keeps simple max-based scales for activations, and uses \emph{AutoQuantize} to
promote sensitive layers. AutoQuantize estimates each layer's sensitivity,
models the cost of each precision, and solves a knapsack-style problem for the
best assignment within a 4.75-bit budget. The routed experts end up in NVFP4,
while attention and Mamba projections use FP8 or BF16
(Table~\ref{tab:precision-fp4}). The process took under two hours on one
8-GPU node, and the result keeps a median of 99.8\% of BF16 accuracy
(Table~\ref{tab:quant-eval}).

\section{Mamba State Quantization}

Reading the Mamba state cache is a bottleneck in memory-bound decoding, so it
is natural to store it in FP16 instead of FP32. On an early checkpoint this
barely changed accuracy but made answers much longer: LiveCodeBench outputs
grew by about 37--40\% (Table~\ref{tab:ssm-cache}), wiping out much of the
speed gain.

The reason is the recurrence. In attention, a rounding error stays in one
cache entry; in Mamba the state feeds back into itself. If storing the state
adds an error $e_t$ at each step, then~\cite{nvidia2026super}
\begin{equation}
  h_{q,t} = h_t + \sum_{i=0}^{t} \left( \prod_{j=i+1}^{t} A_j \right) e_i ,
  \label{eq:error-accum}
\end{equation}
so every past error is still present and, over thousands of steps, they add
up. Fixing this through training is hard, because Mamba-2 is trained with the
chunked SSD algorithm (Section~\ref{sec:mamba2}), which never materialises the
step-by-step cache, so training-free fixes were sought. Round-to-nearest always rounds the same way, so its error is a systematic
bias that accumulates. \emph{Stochastic rounding} (SR) rounds up or down at
random with probabilities proportional to the distance to each neighbour, so
$\mathbb{E}[\operatorname{SR}(x)] = x$ and errors cancel instead of drifting.

Storing the state as INT16 with a scale per 128 values also worked, but FP16
with stochastic rounding was chosen because it needs no scale factors and
Blackwell GPUs have native instructions for it, using the Philox random
generator with five rounds. The lesson is that a state-space layer is not just
a cheaper attention layer: its recurrence creates new failure modes that the
deployment stack must handle.
